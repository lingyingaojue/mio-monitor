> 多机型自适应系统参数监控 App · 纯只读
> 版本：**v0.23.1**（versionCode 50）· 包名：`com.a41probe.monitor` · Kotlin + Jetpack Compose（本机监控 + 局域网双模式）

## 1. 项目概述

A41Probe 是一款**只读系统参数监控**工具，目标机型为中兴天机 A41 Ultra（骁龙 8 Gen1 / SM8450，1×X2 + 3×A710 + 4×A510 三簇 8 核，Adreno 730，1080×2400@60Hz，Android 12 / SDK 31）。

- **三档提权**：免提权 → Shizuku（shell 域）→ Root（su 域），逐级解锁更多受保护 sysfs 节点；授权入口统一在设置页"一键授权（优先 Root）"。
- **5 个主 tab + 5 个整页**：仪表盘 / CPU / GPU / 电池 / 温度（底部悬浮 dock）；设置、传感器、被监控、监控、设备详情为整页二级页（顶栏齿轮或设置页进入）。
- **设计语言**：BiliPai / Miuix（小米 HyperOS 风）——大圆角分组卡片、悬浮液态玻璃底栏、滚动感知玻璃顶栏、明暗双主题；克制动效（数字 tween 滚动、进度弹簧、曲线脉冲收敛）。
- **信任底线**：缺失数据一律置灰/画"–"，不伪造值；所有数值标注数据源与口径；提权未就绪时页面不整块空白，而是给出可读的免提权数据 + 解锁引导。
- **多机型自适应（v0.22+）**：动态分簇（Linux cpufreq policy）、CPU part 微架构识别、GPU 多平台探测（Adreno/Mali/PowerVR）、电源/热区多厂商枚举；A41 真机零回归。详见第 14 章。
- **分层回退 + 平台识别（v0.23+）**：采集层采用「标准 API → sysfs/proc 底层文件 → Shizuku/Root 提权」三级回退；新增 SoC 平台识别器（识别硬件平台而非枚举机型），用于元信息展示与状态语义修正；单位阈值归一化（CPU 频率 100_000 / 电压 100_000 / 电流 10_000）兼容不同厂商 sysfs 单位差异。运行时采集始终以文件存在性探测为准，平台识别不硬编码节点路径。
- **局域网双模式（v0.21+）**：同款 App 双角色——被监控端前台服务常驻、后台每秒采集并经 TCP 推送；监控端 mDNS 自动发现、全自动连接、多设备仪表盘。详见第 13 章。

关键设计：
- **整帧快照**：每次采集产出不可变 `Snapshot`，UI 只消费快照，无逐字段多线程竞态。
- **历史缓冲存原始值**（MHz/%/V/A/W/°C），归一化在图表组件内部动态完成——曲线充满画布且不放大噪声。
- **生命周期驱动**：`ON_START` 启动采集、`ON_STOP`/`ON_DESTROY` 停止采集并注销传感器；退后台零采集零功耗。
- **Reduce Motion**：`rememberAnimatorScale()` 监听 `ANIMATOR_DURATION_SCALE`，用户关动画时所有动画直切（snapTo）。

## 5. 数据采集层

### 5.1 采集循环（MonitorViewModel.start）

```kotlin
while (true) {
    val started = System.currentTimeMillis()
    try {
        val snap = withContext(Dispatchers.IO) { collect() }   // 整帧采集
        updateHist(snap)                                        // 追加历史（60 点）
        _snapshot.value = snap.copy(sampleMs = System.currentTimeMillis() - started)
        _lastSuccessAt.value = System.currentTimeMillis()       // 成功才刷新新鲜度
        _isStale.value = false
    } catch (t: Throwable) {
        if (t is CancellationException) throw t                 // 协程取消不吞
        // 其余异常记日志，跳过本帧
    }
    val elapsed = System.currentTimeMillis() - started
    _isStale.value = System.currentTimeMillis() - _lastSuccessAt.value > 3000  // 停更传导
    delay((1000 - elapsed).coerceAtLeast(100))                  // 固定 1s 节拍
}
```

- 固定 1s 节拍，扣除采集耗时再 sleep，避免滞后累积。
- `isStale`（v20.17）：距上次成功采样 >3s 即为停更，UI 大数字统一变灰。

### 5.2 低层读取（Sysfs）

```kotlin
object Sysfs {
    fun read(path: String): String?    // File(path).readText().trim()，异常返回 null
    fun readInt / readLong / readDouble
}
```

App 域直读，失败返回 null，由 UI 置灰——**不重试不降级不伪造**。

### 5.3 Shizuku 桥（ShizukuBridge）

| 参数 | 值 |
|---|---|
| shell 超时 | `2500ms`（EXEC_TIMEOUT_MS），超时 cancel + destroy 进程 |
| 线程池 | 有界守护池 4 线程（`a41-exec`），防无界增长 |
| 存活进程表 | `ConcurrentHashMap.newKeySet<ShizukuRemoteProcess>()`，超时只销毁自己（per-call holder） |
| stderr | 并行排空（daemon 线程 `forEachLine`），防管道写满阻塞 readLine |
| 状态 | `active` = pingBinder；`authorized` = checkSelfPermission==GRANTED |
| 授权 | `Shizuku.requestPermission(7001)`（主线程调用） |

执行：`Shizuku.newProcess(arrayOf("/system/bin/sh", "-c", cmd), null, null)`，输出 trim 后返回。

### 5.4 Root 桥（RootBridge）

| 参数 | 值 |
|---|---|
| 探测 | `su -c id -u` → 输出 `"0"` 判定可用；`waitFor(2s)` 超时 destroyForcibly（防授权弹窗阻塞 readLine） |
| shell 超时 | `2500ms`；per-call holder + destroyForcibly |
| stderr | `redirectErrorStream(true)` 合并（命令均带 `2>/dev/null`），省一次排空线程 |
| 失权检测 | 连续 5 次 bulk 失败（FAIL_LIMIT=5）→ 置不可用 + 后台线程异步重探测（不阻塞采样） |
| 只读原则 | root 仅用于读取受保护节点（GPU 频率/cpu0 max/背光等），不写任何系统状态 |

### 5.5 电池采集（BatteryReader）

**特征值低频刷新（M20）**：`charge_full/design/cycle/health/tech` 天级变化，启动读一次后 5 分钟刷新（缓存 300s）。

| 节点（/sys/class/power_supply/battery/） | 原始单位 | 换算 | 权限 |
|---|---|---|---|
| `capacity` | % | 原值 | App 域 |
| `status` | Charging/Discharging… | 原值 | App 域 |
| `voltage_now` | μV | ÷1e6 → V | App 域 |
| `current_now` | μA | ÷1e6 → A（UI 取绝对值，符号按充电态标注） | App 域 |
| `power_now` | μW | ÷1e6 → W（**仅 CSV 导出**，UI 功率一律 V×I） | App 域 |
| `temp` | 0.1°C | ÷10 → °C | App 域 |
| `charge_type` | Fast/Standard/Trickle | 映射为 快充/标准/涓流 | App 域 |
| `charge_full` | μAh | ÷1000 → mAh | App 域（5min 缓存） |
| `charge_full_design` | μAh | ÷1000 → mAh（健康度分母） | App 域（5min 缓存） |
| `cycle_count` | 次 | 原值 | App 域（5min 缓存） |
| `health` / `technology` | 字符串 | 映射中文 | App 域（5min 缓存） |

**适配器输入侧**（充电器真实输出，v19 起）：

```kotlin
// 回退路径：usb → ucsi-source-psy-soc:qcom,pmic_glink:qcom,ucsi1 → adapter
// Root 激活时 su 补读（App 域 EACCES、Shizuku 同样 EACCES，仅 Root 可读）
// input_voltage_now（μV→V）+ input_current_now（μA→A），v>0 && c>0 才采用
```

**双口径温度**：sysfs `temp`（内核上报）与 `ACTION_BATTERY_CHANGED` 广播（BatteryManager）各自读取，UI 并排展示差异。

**功率口径（锁定）**：
- UI 功率一律 `V×I`（`powerShown`），充电显示 "+"、放电 "−"。
- `power_now`（驱动平均口径）仅出现在 CSV 导出，不用于 UI。
- 快充判定：**电流 ≥ 2A 或输入电压 ≥ 9V**；`charge_type` 恒为 Fast 不参与判定。

### 5.6 CPU 采集（CpuReader）

```kotlin
// 簇映射（A41 实测拓扑）
0,1,2,3 → A510（小核，4 个）   4,5,6 → A710（中核，3 个）   7 → X2（超大核，1 个）

// 核数：/sys/devices/system/cpu/possible 位图解析（"0-7"），不写死 8
```

**上限读取链（v20.15，60s 缓存）**：
1. `cpu$i/cpufreq/scaling_max_freq`（A710/X2 App 域可读）
2. `cpuinfo_max_freq`（探针 444 权限 App 域全可读，覆盖 A510 scaling EACCES 场景）
3. Root `su cat scaling_max_freq` 补读

> 实测：A41 小核 `scaling_max_freq` 660 权限 EACCES、`cpuinfo_max_freq` 444 权限 App 域可读（1785600 kHz）。

- 当前频率：`scaling_cur_freq` ÷1000 → MHz。
- governor：`cpu0/cpufreq/scaling_governor`（App 域可读）。

**分核占用 + 总占用（需 Shizuku/Root）**：`/proc/stat` 差分，见 §9.1。

### 5.7 GPU 采集（GpuReader）

**占用（免提权）**：
1. 主通道：`/sys/class/kgsl/kgsl-3d0/gpu_busy_percentage`，正则取首个整数，**clamp 0..100**（防驱动瞬态异常）。
2. 备选：`gpubusy`（busy/idle 累计计数）两次采样差分；周期内无计数（深度休眠）返回 null → 曲线断点而非贴底 0%。

**频率（仅 Root）**：节点回退链 `gpuclk → gpu_clk → gpu_clock`（Hz/kHz 兼容：先按 Hz 解释，结果 <1MHz 再按 kHz），再 `devfreq` 目录枚举（含 kgsl/gpu/3d 关键字）。App 域 EACCES、Shizuku shell 域同样 EACCES，仅 Root 可读。
- 频率状态机：有值→OK；已提权读不到→UNAVAILABLE（节点不存在）；未提权→NEED_PRIV。

**温度**：`gpuss-0` / `gpuss-1` 温区（从 Shizuku 批量热区中筛取）。

### 5.8 热区采集（ThermalReader + BulkReader）

- App 域：EACCES（A41 实测全拒），返回 NEED_PRIV。
- **Shizuku/Root 批量采集（BulkReader，每秒 fork 4→1）**：
  - zone type 恒定，首次 `for z in thermal_zone*; echo id|type` 缓存；
  - 每秒一条 shell：`cat 全部 zone temp + cat /proc/loadavg + grep "cpu[0-9]* " /proc/stat`，用 `==LOAD==`/`==STAT==` 分节解析。
- 全部 zone 动态读取（A41 实测 84，本机 iQOO 95），负值/未使能传感器记为 null（灰格）。

### 5.9 系统信息（SysReader）

- `loadavg`：App 域可读（免提权直接给 1/5/15 分钟）。
- `meminfo`：App 域可读，MemTotal 5 分钟缓存（M21），其余字段实时读（文件 ~2KB，1Hz 可接受）；缺 MemAvailable 用 MemFree 兜底。

### 5.10 24h 容量趋势（CapacityHistory）

- 60s 粒度 append 到 `files/a41probe_cap.csv`（`ts,cap`），超过 2000 行裁剪到最近 1440 行。
- 读取时按小时聚合（`ts / 3600_000`，每小时取最后值），只读文件尾部 1450 行。

### 5.11 传感器（MonitorViewModel.registerSensors）

- **仅传感器页可见时注册**（DisposableEffect），离开即注销（S4）。
- 5 类实时通道：加速度计/陀螺仪/磁力计/光线/距离，`SENSOR_DELAY_NORMAL`。
- 按类型各自限频 200ms（事件型不被连续上报型吞掉），`_sensorsLive.update` 原子更新。
- 页面列出手机全部传感器（`SensorManager.getSensorList`，A41 实测 28 个）。

### 5.12 提权矩阵（A41 探针实测锁定）

| 数据 | App 域 | Shizuku | Root |
|---|---|---|---|
| 电池全套（容量/电压/电流/温度/health/cycle…） | ✅ | ✅ | ✅ |
| CPU 当前频率 / governor / time_in_state | ✅ | ✅ | ✅ |
| cpu0-6 scaling_max_freq、cpuinfo_max_freq | ✅ | ✅ | ✅ |
| cpu7（X2）scaling_max_freq | ❌ EACCES | ❌ | ✅ |
| GPU 占用（gpu_busy_percentage） | ✅ | ✅ | ✅ |
| GPU 频率（kgsl/devfreq） | ❌ | ❌ | ✅ |
| 热区 84 zone / /proc/stat / loadavg | ❌ | ✅ | ✅ |
| 充电器输入侧 V×A | ❌ | ❌ | ✅ |
| 背光 | ❌ | ❌ | ✅ |

> 提权优先级：Root 可用则走 su 通道（BulkReader.readRoot），失败/失权自动回落 Shizuku（readShizuku），都没有则 App 域——不互斥跳过。

## 6. 数据模型与口径（锁定，勿改）

| 模型 | 关键字段 | 口径 |
|---|---|---|
| `BatteryData` | capacity/voltage/currentA/powerW/tempC/tempBmC/chargeFull/chargeDesign/cycleCount/health/status/tech/chargeType/inputVoltV/inputCurA | 见 §5.5；`healthPercent = chargeFull×100/chargeDesign`；`isCharging = status=="Charging"`；`currentDisplay = abs(currentA)`；`powerShown = V×I` |
| `CpuCore` | index/cluster/freqMHz/maxMHz | MHz；簇映射见 §5.6 |
| `GpuData` | busyPercent/freqMHz/freqState/temp0C/temp1C | 占用 clamp 0..100 |
| `MemInfo` | totalKB/freeKB/availKB/cachedKB/swapTotalKB/swapFreeKB | 1GB=1048576KB；usedPercent=(total-avail)×100/total |
| `ThermalZone` | id/name/tempC/state/priv | m°C÷1000 |
| `Snapshot` | +shizukuActive/serviceUp/authorized/rootAvailable/sampleMs/**isStale** | maxThermal 只取 cpuss/cpu/gpuss 前缀（tof/skin 不顶替结温）；thermalAvg 只统计 >0 有效值 |

**显示规则（信任底线）**：`-273`（未使能）/未使能/缺失 → 一律灰格或"–"；`DataState` 状态机 OK/NEED_PRIV/UNAVAILABLE/STALE 驱动 UI 文案（"需 Shizuku"/"不可用"/"停更"）。

## 7. UI 设计系统（v3.0：BiliPai / Miuix）

### 7.1 设计语言

v3.0 起界面换成 **BiliPai 的 Miuix 视觉语言**（小米 HyperOS 风）：大圆角分组卡片、悬浮液态玻璃底部 dock、滚动感知的玻璃顶栏、居中标题 + 圆形返回的二级页、Miuix 设置分组行；支持**浅色 / 深色 / 跟随系统**三档与 6 套配色预设（各自动派生深色）。

### 7.7 曲线归一化算法（Charts.NormScope）

```kotlin
// 动态窗口归一化：以窗口中心为锚，span = max(半幅, max×minRatio 0.25)
//   y = 0.5 + ((v - center) / span).coerceIn(-1, 1) × 0.44   → 0.06..0.94 安全区
// 恒值/窄幅（span≤0）→ 画中线（不放大噪声）；真实大幅变化充满画布
// 固定量程 NormScope.fixed(center, half)：GPU 占用 0..100（fixedRange=100f）、
//   电压 3.9V±0.6（fixedCenter=3.9, fixedRange=1.2）
```

**末点平滑**：`rememberSmooth` 将最新点从旧值 tween 过渡到新值（380ms），历史点不变——波形平滑滚动，1Hz 采样下大部分时间静止。

**槽位映射**：固定 60 槽，最新点恒在最右端，历史向左滚动；点数不足左侧留空；稀疏序列（如 24h 24 点）`stretchToFull` 按点数铺满。

### 7.8 液态玻璃（v3.3，双引擎）

**引擎选择**（`ui/glass/MioLiquidPolicy.kt`，纯函数可单测）：
| 条件 | 引擎 | 说明 |
|---|---|---|
| FULL + API ≥ 33 | **Miuix Backdrop 液态玻璃** | BiliPai 同款：背板录制 + vibrancy + blur + 边缘折射(lens/色散) + BloomStroke 高光 + 投影/内阴影 |
| FULL + API 31/32 | Haze 实时模糊 | Miuix Backdrop 依赖 Android 13 的 RenderEffect/RuntimeShader |
| LITE | 仅壳层 Haze | 卡片半透明不模糊，省电 |
| OFF / API < 31 | 实色 / 半透明降级 | 系统无实时模糊 |

**两条渲染路径**（`ui/glass/MioGlassSurfaces.kt`）：

*A) Miuix Backdrop 液态玻璃（API 33+，DOCK/CHROME/INDICATOR）*
1. 内容录制：`MainActivity` 的 `MioChromeContent` 挂 `rememberChromeBackdropSource(...)`（`layerBackdrop` + 内容 layer 录制），通过 `LocalMioChromeBackdrop` 下发；API<33/LITE 时改回 `hazeSource`；
2. `Modifier.drawBackdrop(backdrop, shape, effects, highlight, layerBlock, onDrawSurface)` 合成：
   - `colorControls(saturation)` 增艳（玻璃下内容更"透亮"）；
   - `blur(背板模糊)`；
   - `lens(refractionHeight, refractionAmount, chromaticAberration)`——设计系统 `core/ui/effect/LiquidLens.kt`（Kyant AGSL 折射 + 色散），壳体无色散、指示器 0.4；
   - `Highlight + BloomStroke`：双光源边缘 bloom 高光（BiliPai 同款参数）；
   - `onDrawSurface`：玻璃底色（lerp(白/深底, accent, tintMix) × surfaceAlpha）+ 可读性 scrim；
   - `dropShadow` + Compose `innerShadow`：悬浮投影 + 底部内阴影（厚度感）。

*B) Haze / 半透明降级（API 31/32、CARD、SHEET）*
- 单 tint + 低不透明度 + 1dp rim + 1.2dp 折射环 + 镜面 sheen（v3.2 材质，参数见下表）。

**参数表**：
| 表面 | A) Backdrop（33+，浅/深） | B) Haze 降级 |
|---|---|---|
| DOCK | 底色 α0.30/0.40，blur 10dp，饱和 1.5，折射 20/22dp，bloom 0.85，投影 14dp | α0.26/0.34，blur 32dp |
| CHROME | 底色 α0.06→0.34（随滚动），blur 4→14dp，折射 6→14 / 8→16dp，bloom 0.35→0.65 | α0.06→0.36，blur 10→32dp |
| INDICATOR | accent tint 0.9，blur 4dp，折射 8/12dp，色散 0.4，bloom 0.80 | accent α0.20，blur 14dp |
| CARD | 不用 Backdrop | α0.34/0.42，blur 24dp（仅 FULL），折射环 0.18/0.22 |
| SHEET | 不用 Backdrop（窗口模糊 28dp） | α0.62/0.68 |

**宿主与三个源**（`ui/glass/MioGlassHost.kt`）：
| 名称 | 内容 | 消费者 |
|---|---|---|
| `pageState`（Haze，背景层） | 页面底色 + 环境光 + 角色立绘 | 内容卡片 |
| `chromeState`（Haze，内容层，API<33 / LITE） | 各屏 UI | Haze 顶栏/dock/返回条 |
| `chromeBackdrop`（Miuix Backdrop，内容层，API33+ FULL） | 各屏 UI 录制 | BiliPai FloatingBottomBar、液态玻璃顶栏/返回条 |

`ScrollAware` 回写滚动进度，顶栏按 `resolveChromeProgress` 做 0→1 的模糊/折射/着色渐强。

**能力矩阵**：
| 档位 / 系统 | API 26–30 | API 31–32 | API 33+ |
|---|---|---|---|
| FULL（完整） | 半透明材质（无模糊） | Haze 全表面实时模糊 | **Miuix Backdrop 液态玻璃（折射 + 高光）** |
| LITE（简约） | 半透明材质 | 仅壳层 Haze，卡片半透明 | 仅壳层 Haze |
| OFF（关闭） | 实色 | 实色 | 实色 |

**设置页自检**：「外观 → 玻璃引擎」只读行显示当前实际路径（`Miuix Backdrop 液态玻璃` / `Haze 实时模糊` / `半透明降级` / `实色`），用于排查"看起来不像玻璃"。

**性能**：API33+ 同时只有 3 个 Backdrop 消费面（dock/顶栏/返回条），背板只录制一次；LITE/OFF 是省电逃生档；卡片保持 Haze 低采样，不冻结视频/图片。

### 7.10 OriginOS 实验调校（v3.5）

**背景**：ADB 实测确认 vivo/iQOO OriginOS 封了 `settings put`（exit=0 静默丢弃），但 `content insert` 对无冒号值可写、`settings delete` 可删、`settings get` 可读。文件里实测可用的 4 项系统设置因此接入 App（其余假/不安全项不做）。

**数据层**（`data/toolbox/`）：
| 文件 | 职责 |
|---|---|
| `OriginSettings.kt` | 纯逻辑：功能白名单/命名空间/key、插帧值格式、刷新目标、命令构造（`settings delete` + `content insert`）、注入校验、`content query`/`settings get` 解析、vivo 设备门槛 |
| `OriginSettingsBridge.kt` | 读：Settings API → Root/Shizuku `settings get` 兜底；写：ADB 授权直写 > Root > Shizuku shell，逐通道回读校验、失败自动降级；首次写入前备份原始值 |
| `ToolboxConfig.kt` | SharedPreferences `mio_toolbox`：确认状态、守护、插帧/刷新参数、每 key 原始值备份 |
| `ToolboxController.kt` | 唯一状态机（StateFlow）：refresh / setFeature / setInterpolation / setRefreshTarget / restoreAll(toOriginal) / applyEnabledFeatures |
| `ToolboxGuardService.kt` | 可选前台守护（5s 轮询重写被系统重置的 key，默认关闭） |
| `ToolboxBootReceiver.kt` | 开机后若守护开启则重启服务 |
| `ToolboxShellWriter.kt` | Shizuku/Root 通道的 `app_process` 直写器：以 shell 身份经 `IContentProvider.insert` 写 SettingsProvider，用于 `content insert` 不支持的带冒号值（插帧） |

**UI**：`ui/screens/ToolboxScreen.kt`（设置 → 实验功能），设备与权限卡片每秒刷新，含写入通道自检（区分 global 可直写 / system 需 Shizuku-Root）、四项开关 + 风险二次确认、插帧/刷新弹层、守护、恢复（默认/原始值）；非 vivo 设备只读。

**写入策略（Android 17 真机结论）**：
1. `WRITE_SECURE_SETTINGS` 已授权且 key 属 global → `Settings.Global.putString` 直写成功；
2. system 命名空间即使 App 有 `WRITE_SECURE_SETTINGS` 也会被拒（"You cannot keep your settings in the secure settings."），`WRITE_SETTINGS` 又由 role 管理不可授予；
3. Root / Shizuku（shell uid）通道：删除用 `settings delete`；写入用 `app_process` 启动 `ToolboxShellWriter` 直调 SettingsProvider（`insert`），可写含冒号的值，同时绕开 vivo 对 `settings put` 的静默丢弃；
4. 每通道写后统一回读；不一致自动尝试下一通道，最终失败给出明确错误。key/value 均白名单校验，禁止任意 shell 拼接。

**测试**：`OriginSettingsTest` 覆盖命令字符串、注入拒绝、值格式往返、状态判定、写入值映射、adb 输出解析、设备门槛；真机验证脚本通过 debug-only `ToolboxDebugReceiver`（受 `WRITE_SECURE_SETTINGS` 保护）驱动四项功能、回读校验与守护重写。

### 7.11 全局玻璃透明度 / OriginOS「高级材质」对齐（v3.6 → v3.7）

**目标**：玻璃不是白蒙蒙的磨砂，而是 OriginOS 高级材质式的「强实时模糊 + 透彩色 + 低填充 tint + 边缘高光」。四档只缩放玻璃填充 alpha，可读性 scrim 与正文颜色不变；「低」档本身就是参考观感，中/高/全透逐级更透。

| 档位 | label | 因子（v3.7） | 说明 |
|---|---|---|---|
| LOW | 低 | 1.00 | OriginOS 参考档：强模糊 + 透彩色 + 低填充 |
| MEDIUM | 中 | 0.80 | 默认，比参考更透一点 |
| HIGH | 高 | 0.58 | 明显更透 |
| ULTRA | 全透 | 0.38 | 最透，卡片 tint=0、blur=0 |

**v3.7 材质基准（LOW = 1.0）**：
- Haze（`GlassPolicy.kt`）：CARD 填充 0.14/0.18（浅/深）、blur 32dp、lens 0.24/0.28；CHROME 0.24/0.30；DOCK 0.16/0.22；INDICATOR 0.14/0.18；SHEET 0.58/0.64。仅实时模糊路径加 **Haze ColorFilter 饱和度增艳**（`resolveGlassVibrancy`：CARD 1.45 / DOCK 1.40 / CHROME 1.35 / SHEET 1.15），这就是「透彩色」的来源。
- Miuix Backdrop（`MioLiquidPolicy.kt`）：DOCK surfaceAlpha 0.22/0.28、saturation 1.65；CHROME ramp 0.04→0.24（浅）/ 0.06→0.30（深）、saturation 1.55；INDICATOR 0.14/0.18、saturation 1.60；覆盖层卡片 0.16/0.22；`colorControls` 增加 contrast 1.05 / brightness 0.01。

### 7.12 PrismalAGSL 卡片液态玻璃（v3.9）

**选型**：[PrismalAGSL](https://github.com/styropyr0/PrismalAGSL) v1.0.6（MIT，JitPack）：Compose 液态玻璃库，自带 backdrop 采样、模糊、圆角 SDF 折射、**chromatic aberration（RGB 色散）**、三档自动降级。Mio 只把它的绘制管线用于「卡片玻璃」；顶栏/底栏/弹层保留 Miuix/Haze 引擎（底栏必须保持 BiliPai 原版）。

**依赖**：
- `settings.gradle.kts` → `maven(url = "https://jitpack.io")`
- `gradle/libs.versions.toml` → `prismal = "v1.0.6"`、`prismal-glass = { group = "com.github.styropyr0", name = "PrismalAGSL", version.ref = "prismal" }`
- `app/build.gradle.kts` → `implementation(libs.prismal.glass)`
- 许可：仓库 LICENSE 为 MIT（发布 POM 元数据误标 Apache-2.0），已记入 `THIRD_PARTY_NOTICES.md`。

**卡片层结构（从底到顶）**：
1. `MioBackdropLayer`：`MioAmbientBackground`（环境光渐变）+ `MioArtBackground`（立绘），被 `Modifier.prismalGlassLayer(...)` 录成 Prismal 背板；同一层还挂 Haze `pageState` 供降级。
2. 卡片 `Modifier.drawPrismalGlass(...)`（v3.9 不用 `PrismalGlassSurface`，避开默认 specular 白色高光）：
   - `prismalBlur(4.dp)`（**全透档跳过**）；
   - `colorControls(brightness=-0.02f, contrast=1.06f, saturation=1.55f)`（只提艳，不铺白）；
   - `prismalLens(refractionHeight=24.dp, refractionAmount=64.dp, depthEffect=true, chromaticAberration=0.55f)`（API33+ AGSL 真实边缘弯折 + RGB 色散；低版本无 lens）；
   - `specular=null`，`depthShadow={ PrismalDepthShadow.Default }`（黑色悬浮投影）；
   - `onDrawSurface`：`prismalCardTintAlpha(...)` 缩放 tint（浅色基准 0.04 / 深色 0.07 × 四档倍率，clamp 0.02–0.12；**全透=0**）；
   - `onDrawFront`：1px 中性白边（全透 alpha 0.12，其他 0.22）。
3. 卡片内容：`MioCard`/`MioPreferenceGroup` 的 Column（文本、数字、图表、进度条）。
4. 壳层：顶栏、BiliPai dock、弹层，属于独立叠层，不参与卡片绘制。

**全透档（原「极高」）**：`prismalCardTintAlpha(ULTRA)=0`、`prismalBlur` 跳过，只保留 lens/1px 边/投影；立绘直接透出。设置页标签「极高」→「全透」，语义仍是四档第 4 档。

**删除人工彩边（v3.9）**：移除 `mioGlassEdgeDispersion` 及 `resolveGlassEdgeDispersion`；真实色散只来自 Prismal 卡片 lens + Miuix 顶栏/dock/胶囊的 `lens(chromatic)`，Haze 降级只保留白色折射环。

**壳层色散**：Miuix 液态参数（DOCK 0.35、CHROME 0.25、INDICATOR 0.50、覆盖层卡 0.30）；BiliPai `scaleBottomBarTuning` 追加 `shellChromaticAberrationAmount = 0.35f`、`indicatorChromaticAberrationAmount = 0.50f`，scrim/透明度不动。

**弹窗/弹层可读性（v3.9）**：
- 新增 `MioDialogStyle.kt`：`MioDialogContainerAlpha = 0.92f`（固定，不随四档缩放）、`MioSheetMinFillAlpha = 0.72f`、`MioDialogBackdropBlur()`（`ModalWindowBlurBehindEffect`，API31+）；
- Toolbox/Monitor 的 `AlertDialog` 统一改用 `Ink.glassFill.copy(alpha=MioDialogContainerAlpha)` + 窗口模糊，文字仍 `Ink.tx/Ink.tx2`；
- `GlassPolicy.SHEET` 基础填充抬到 0.80/0.84，`applyGlassGeometryTransparency(..., floorAlpha=MioSheetMinFillAlpha)` 保证极高档也不低于 0.72。

**降级与回退**：API<33、LITE、OFF 不启用 Prismal 卡片（继续 Haze）；若实机明显掉帧，先降 `prismalLens` refractionAmount 64→48dp、blur 4→2dp，仍不行回退 Haze 卡片。

**测试**：`PrismalCardPolicyTest`（tint 浓度/全透=0、启用门槛）、`DialogSurfacePolicyTest`（弹窗 0.92、SHEET 四档 ≥0.72、深色不低）、其余既有玻璃测试；全量 48 项单测 + lint。

### 7.14 触感强度修复与立绘四档（v3.11）

**触感强度为什么之前“不生效”**：旧实现把三档差异主要压在 `VibrationEffect` 振幅（90/165/255）和系统常量上。部分 vivo/iQOO ROM 虽然报告 AMPLITUDE_CONTROL，但会忽略 App 振幅，三档最终都变成同一条 10s 连续震动；`play()` 里 MEDIUM/HEAVY 又都走 `LONG_PRESS`，差异只剩一段可能被压到 scale 0 的裸脉冲 —— 听起来自然“没区别”。

**v3.11 执行曲线**（`ui/components/MioHaptics.kt`）：
- 新增三档纯映射：
  - 点按：轻 1×8ms/amp80；中 1×20ms/amp170；重 2 脉冲 28ms+16ms（中间 18ms 间歇）/amp255+180；Tab 切换同档略短。
  - 按住：轻 10ms 振/14ms 停；中 22ms/6ms；重 40ms/2ms（接近连续），`repeat=0` 循环，松手 `cancel`。
- 强度不再依赖 ROM 是否尊重振幅：**节奏、脉冲数、时长**本身即可区分；支持振幅的机型再叠加强弱。
- `set()` 时重新读取系统「触感反馈」总开关；无马达/波形被拒绝时退回 `performHapticFeedback` 系统常量，仍不崩溃。
- 纯 JVM 测试 `HapticPatternPolicyTest`：波形长度/首项 0、能量递增、重档双脉冲、Tab 短于点按、按住占空比轻>中>重、峰值振幅递增。

**立绘四档**（`ui/theme/Palette.kt` + `ui/components/MioBanner.kt`）：
| 档位 | 高度 | 说明 |
|---|---|---|
| 关闭 | 0 | 不画立绘 |
| 小 | 300dp | 只占下半屏小部分 |
| 中 | 420dp | 默认，与旧版完全一致 |
| 大 | 540dp | 角色明显放大，背景纹理更满 |

- `ThemeConfig` 新增 `KEY_ARTWORK_SIZE="artwork_size"`；旧 key `show_artwork` 保留：
  - 启动时若新 key 存在读 ordinal；不存在则按旧 boolean 迁移（true→中，false→关闭）。
  - `setArtworkSize()` 同时写新 key + 旧 boolean；保留 `setArtwork(ctx, Boolean)` 兼容旧调用。
- `MioArtBackground(art, size)` 用 `size.heightDp.dp` 替换固定 420dp；默认 MEDIUM，旧观感不变。
- 设置页「显示角色立绘」开关改为与「界面质感」同款 `SegmentSetting`：关闭 / 小 / 中 / 大。
- 测试 `ArtworkSizePolicyTest`：四档标签、高度顺序、旧 boolean 迁移、非法 ordinal 兜底。

**底栏接入**：`FloatingBottomBar.kt` 内部 `rememberHapticFeedback(NAVIGATION)` 已替换为 Mio `rememberHaptics()`，所以 BiliPai dock 的点击/拖拽刻度也走「轻/中/重」曲线（vendored 补丁见 `design-system/VENDORED.md` 第 3 条）。\n\n**验收**：触感三档按住/点按可明显区分；立绘四档切换立即生效、重启保持；旧用户升级后立绘按旧开关落到中/关闭。
### 7.15 温度页 ADB 全量热数据（v3.12）

**目标**：把 Shizuku/Root/ADB 能读到的热数据全部纳入温度页，不再写死 84 区或冷却白名单。

**实测数据源（iQOO Neo10 Pro+）**：
- `/sys/class/thermal/thermal_zone*` 共 95 个；经非温度节点/哨兵/长期不更新过滤后约 80+ 个有效温度；
- `/sys/class/thermal/cooling_device*` 共 64 个（cpufreq/cpu-hotplug/cpu-cluster/pause/thermal-pause/kgsl/ddr/ufs/display-fps/battery/modem/PA/MMW 等）；
- 每区 `trip_point_*_{temp,type}`：passive（降频）/ active / hot / critical；
- `dumpsys thermalservice`：Current temperatures（已解析）、阈值（已解析）、Current cooling devices（本版本不重复展示）。

**数据层**：
- `Models.kt` 新增 `ThermalTrip(type, tempC)`，`ThermalZone.trips` 默认空列表；
- `BulkReader` 首读缓存 `TRIP_SCAN_CMD` 的 zone→trip 映射（m°C→°C，按温度升序），后续采样只读 temp；
- `BulkReader` 的 cooling 改为**全量**（`meta.keys`），每秒一次 shell 内读取全部 64 个 `cur_state`；metadata（type/max_state）仍首读缓存；

**UI**：
- 新文件 `ThermalGrouping.kt`：`groupThermalZones` 将全部 zone 分为 **CPU / GPU / NPU·内存·多媒体 / 射频·充电·外壳 / 其他** 五组，保证互斥且无遗漏；`visibleZoneRows` 实现默认 Top-5 / 展开全部；`tripThresholdLabel` 过滤 <20°C 的低温触发阈值后取最低有效阈值。
- `ThermalScreen` 的 CPU/GPU 卡片复用「热缓解动作」卡的折叠样式：默认 Top-5，底部“查看全部 N 项”，展开后看全部；CPU/GPU 展开时追加 HAL 官方温度（type 0/1）。
- 其他分组同样可展开；底部网格改 `AllZonesGrid`，不再 `take(84)`；页头数量动态。
- 热缓解动作展开显示全部 64 项；`coolingZh` 扩充 cpufreq/cpu-hotplug/cpu-cluster/pause/thermal-pause/kgsl 等本机类型。

**测试**：
- `ThermalGroupingPolicyTest`：分组互斥/无遗漏、CPU/GPU 归属、Top-5/展开、trip 取最低有效阈值、无效温度排序；

**性能与降级**：全量 cooling 仍合并进同一 bulk shell 调用；若实测 `sampleMs` 明显上升，可将非活跃 cooling 降为每 2s 刷新，active 仍 1s。无权限时保持电池温度兜底，不伪造数据。

## 9. 关键算法

### 9.1 /proc/stat 差分（CPU 占用）

```
每帧读 "cpu " 行（总数）与 "cpu0-7" 行（分核）：
  total = 全部数值字段和；idle = 字段[3](idle) + 字段[4](iowait)
  占用% = (Δtotal - Δidle) / Δtotal × 100，clamp 0..100
首采样无基线 → null（UI 置灰）；缺核 → null
Shizuku 失权时复位分核/总占用曲线（不冻结旧值冒充实时）
```

### 9.2 GPU 占用（gpu_busy_percentage）

免提权主通道直接读百分比整数（clamp 0..100）；无该节点的机型回退 `gpubusy` 累计计数差分。

### 9.3 档位驻留（time_in_state）

```
读 cpu0/stats/time_in_state："freq(kHz) 累计时间(ms)"
占比 = 单档时间 / 总时间；MHz = kHz/1000
```

### 9.4 健康度

`healthPercent = charge_full × 100 / charge_design`（两者同为 μAh→mAh 换算，比率不受影响）。

### 9.5 停更传导（v20.17）

`isStale = now - lastSuccessAt > 3000`，每采样拍更新；UI 大数字在 stale 时改 Ink.off（灰）。

## 10. 构建与发布

1. 修改 `app/app/build.gradle` 的 `versionCode`/`versionName`（bump 脚本）。
2. 固定命令后台构建（§2.1）。
3. **dex 验证**（`verify_v20XX.py`）：zipfile 读全部 dex 合并，校验版本串与新功能字符串常量（**勿用 Kotlin 注释/类前缀**——注释不进 dex，字段在字符串池中是短名）。
4. `Copy-Item` 到桌面 `A41Probe-vXX.YY.apk`，`present_files` 交付。
5. 用户手动安装真机验收（构建→桌面→用户装测是常态闭环）。

### 13.1 设计目标与角色
同款 App、双角色，入口在设置页「局域网双模式」卡：
- **被监控端 Agent**：前台服务常驻，后台每秒采集本机全部参数，经 TCP Server 向所有已连接监控端推送；支持免提权/Shizuku/Root 三档；用户可一键终止。
- **监控端 Monitor**：mDNS 自动发现局域网内 Agent，全自动连接、断线退避重连；多设备仪表盘，每张设备卡展示全部参数并标注对方权限档；点卡进设备详情复用全套图表。

### 13.2 服务发现（mDNS / NSD）
- 服务类型 `_a41probe._tcp.`（末尾点）；AgentNsd serviceName="型号-端口" 保证唯一。
- TXT 属性：name / model / brand / soc / appVer / priv。
- Agent 端 `NsdManager.registerService`：注册 listener 存为字段 `regListener`，注销必须传同一引用；registering/registered 双 @Volatile 标志，注册进行中被 stop 也能用保存 listener 取消（修复 NSD 残留）。
- Monitor 端 `MonitorNsdDiscovery.discoverServices`：NsdManager 同一时刻只允许 resolve 一个，用 ConcurrentLinkedQueue 串行 pumpResolve；每次 resolve 起 5s 看门狗，回调缺失也能复位继续。

### 13.3 传输协议（TCP + 长度前缀帧）
- 帧：4 字节 big-endian 长度 + UTF-8 JSON，MAX_FRAME 2MB（实测全指标快照 <8KB）。
- writeFrame：synchronized(out) + flush；readFrame：readFully 正确处理半包/粘包，EOF（含载荷截断）返回 null。
- 消息（被监控端→监控端单向，监控端只收不发）：
  - `hello`：type + device（RemoteDeviceInfo 全字段含 priv）；
  - `snapshot`：type/ts/priv + cpu/gpu/thermal/cooling/battery/mem（cooling 在 root 层、不在 thermal 内）；
  - `bye`：服务终止。
- **换算在被监控端完成、监控端只展示**，两端口径一致（见第 6 章）。

### 13.4 被监控端 AgentService
- 前台服务：onCreate 建通知渠道并 startForeground；Android 14 用 FOREGROUND_SERVICE_TYPE_SPECIAL_USE（Manifest 声明 + specialUse property）。
- onStartCommand：ACTION_STOP→shutdown 返回 START_NOT_STICKY，否则 start() 并返回 START_STICKY（系统杀进程后自动重建）。
- onDestroy 重写兜底：任何非 ACTION_STOP 销毁路径都走 shutdown；shutdown 幂等（shuttingDown 守卫），末尾 scope.cancel()。
- 协程（SupervisorJob + Dispatchers.IO）：accept 循环；采集广播循环（每秒 collector.collect()，首次成功后才注册 NSD、才允许发 hello 保证 priv 正确，向所有 Conn 的 outgoing Channel trySend）；每连接 handleClient（立即发 hello、reader 检测 EOF 立即收尾、写循环）。
- 防杀后台策略：①常驻前台通知（白色剪影 ic_stat_agent）；②引导加入电池优化白名单（REQUEST_IGNORE_BATTERY_OPTIMIZATIONS）；③锁屏保持（PARTIAL_WAKE_LOCK 12h 上限 + WIFI_MODE_FULL_HIGH_PERF WifiLock，KEY_KEEP_AWAKE，切换后重启服务生效）。
- shutdown：发 bye、关全部 socket/server、注销 NSD、释放锁、cancel scope、清 AgentState、stopForeground + stopSelf。

### 13.5 监控端 MonitorRepository（object 单例）
- DeviceEntry key="host:port"，字段 serviceName/host/port/info/snap/state/latencyMs/source(DISCOVERED|MANUAL)/log。
- 连接状态机 connect()：Socket.connect 超时 3s（connect 耗时记 latencyMs）；连上后 soTimeout=15s（约 15 个快照周期无数据判断链，防对端硬断电无 FIN 假死在线）。
- connSockets 映射：重连/移除/停止时先 close 旧 socket 唤醒阻塞读、再 cancel Job，避免僵尸协程与重复 TCP；读循环每帧 ensureActive()。
- 断线指数退避 1s→60s；**收到 Hello 才重置退避**（TCP 连上但应用层未就绪不重置，防快循环）。
- 自愈：设备离线后 mDNS 重新 resolve，处于待连/离线态且无活连接时自动重连；Bye 视为对方终止、不重连。
- 生命周期：进入监控页 start（发现 + 连接）；离开页 stopDiscovery（仅停扫描省电、保活已建连接）；手动添加 manualAdd（IP + 端口）。
- 偏好 prefs "a41_monitor"：auto_connect / auto_reconnect（默认 true）。

## 14. 多机型自适应（v0.22+）

v0.22 起从「仅深度适配 A41 Ultra / SM8450」泛化为「自适应常见安卓机型与 CPU/SoC」，核心原则：**一切从 sysfs/proc 动态读取，不写死机型参数**；A41 真机零回归。

### 14.1 动态分簇（Linux cpufreq 标准，全平台通用）

- **核数**：解析 `/sys/devices/system/cpu/possible` 位图（如 `0-7` → 8 核），兼容 `0-3,6-7` 离散格式。
- **分簇**：枚举 `/sys/devices/system/cpu/cpufreq/policy*/`，读每个 policy 的 `related_cpus`（回落 `affected_cpus`、再回落 `cpuinfo_shared_cpu_list`），共享同一 policy 的核归为一簇；policy 列表本身即簇。
- **格式兼容**：`related_cpus` 可能是空格分隔 `0 1 2 3`、范围 `0-3`、或混合 `0-2,4,5`，`parseCpuList()` 用正则 `[\s,]+` 分割后逐 token 解析范围或单值。
- **每簇 maxMHz**：读该簇首个核的 `cpuinfo_max_freq`（kHz÷1000），回落 `scaling_max_freq`，App 域读不到时走 Root 补读链（与 CpuReader 一致）。

### 14.2 CPU 微架构识别（MIDR part number）

- 解析 `/proc/cpuinfo` 每个逻辑核的 `CPU implementer` + `CPU part`（十六进制），用 **(implementer, part) 二元组** 映射 Cortex/X 型号。
- **关键 part 表**（ARM 官方 + Linux 内核 cputype.h）：

| part | 核心 | 架构 | part | 核心 | 架构 |
|---|---|---|---|---|---|
| 0xd03 | A53 | ARMv8 | 0xd46 | A510 | ARMv9 |
| 0xd05 | A55 | ARMv8.2 | 0xd47 | A710 | ARMv9 |
| 0xd07 | A57 | ARMv8 | 0xd48 | X2 | ARMv9 |
| 0xd08 | A72 | ARMv8 | 0xd4d | A715 | ARMv9 |
| 0xd09 | A73 | ARMv8 | 0xd4e | X3 | ARMv9 |
| 0xd0b | A76 | ARMv8.2 | 0xd82 | X4 | ARMv9 |
| 0xd41 | A78 | ARMv8.2 | 0xd85 | X925 | ARMv9 |

- **implementer**：`0x41`=ARM（MTK/Tensor/Exynos公版/麒麟手机核）、`0x51`=高通（Kryo 6xx/7xx 复用 ARM part 编号）、`0x53`=三星 Mongoose、`0x48`=海思泰山（服务器核）。无 MediaTek implementer 码。
- **回退命名**：识别不到时按簇 maxMHz 从低到高用通用名「小核/中核/大核/超大核」。
- **refresh 变体**（如 A510 r0p2/r1p0）part 不变，靠 `CPU variant` 区分，不影响 label。

### 14.3 拓扑模型与颜色角色（CpuTopology.kt）

- `data class CoreCluster(label, cpuIndexes, maxMHz, colorRole)`，`data class CpuTopology(coreCount, clusters)`。
- `ClusterRole` 按簇 maxMHz 降序分配：

| 簇数 | 最大簇 | 次大簇 | 第三簇 | 最小簇 |
|---|---|---|---|---|
| 1 | PRIME 暖橙 | — | — | — |
| 2 | PRIME 暖橙 | — | — | EFFICIENCY 青绿 |
| 3 | PRIME 暖橙 | PERFORMANCE 蓝 | — | EFFICIENCY 青绿 |
| 4 | PRIME 暖橙 | PERFORMANCE 蓝 | BALANCE 紫 | EFFICIENCY 青绿 |

- 色值与旧版 A41 完全一致：PRIME=`#E07B39`（原X2）、PERFORMANCE=`#4A86D8`（原A710）、EFFICIENCY=`#2F9E8F`（原A510）、BALANCE=`#9B59B6`（新增，仅4簇机型）。
- **缓存**：拓扑恒定，`@Volatile` + `synchronized` 双重检查，启动读一次后缓存；`invalidate()` 可在授权状态变化时清缓存重探。
- 全链路 `CpuCore.cluster` 从固定枚举改为 String label，`CpuCore.colorRole` 新增角色字段；远端协议不下发 colorRole，监控端按 label+maxFreq 降序重推断（规则与本机一致）。

### 14.4 GPU 多平台探测

优先级链（GpuReader）：

| 平台 | 频率节点 | 占用节点 | 单位 |
|---|---|---|---|
| 高通 Adreno | `/sys/class/kgsl/kgsl-3d0/gpuclk`（回落 `gpu_clk`） | `gpu_busy_percentage`（回落 `gpubusy` 差分） | Hz/kHz 自动换算 |
| Mali（MTK/Exynos） | `/sys/kernel/gpu/gpu_clock` | `/sys/kernel/gpu/gpu_busy` | **MHz 直读，不÷1e6** |
| MTK 备用 | — | `/sys/module/ged/parameters/gpu_loading` | 百分比 |
| PowerVR/IMG | `/sys/class/devfreq/*pvr*/*img*/*powervr*/cur_freq` | — | Hz |
| 通用回退 | `/sys/class/devfreq/` 任何含 `kgsl/mali/gpu/3d/pvr/img/powervr` 的设备 `cur_freq` | — | Hz |
| 老MTK PowerVR（v0.22.1+） | `/sys/kernel/ged/hal/current_freqency`（驱动拼写freqency）→ `/proc/gpufreq/gpufreq_var_dump` → `/proc/gpufreq/gpufreq_opp_dump` | `/sys/module/ged/parameters/gpu_idle`（占用=100-idle） | kHz/1000 |

- 占用全部缺失时置 `null`（UI 显示「–」），频率仍尽量显示。
- `freqRaw`/`freqNode` 进 CSV RAW，供排查。

### 14.5 电源输入侧多厂商枚举

- 枚举 `/sys/class/power_supply/*` 下所有节点，读 `type` 字段，过滤含 `USB/DCP/CDP/Wireless/Mains`（排除 `Battery`）。
- 对符合条件的节点读 `voltage_now` + `current_now`（µV/µA），有正值则返回 `AdapterInput`。
- 覆盖：高通（`usb` / `ucsi-source-psy-*` / `adapter`）、MTK（`usb` / `charger` / `wireless`）、Exynos（`usb` / `wireless` 固定名）。
- **快充判定**：电池电流≥2A 或输入 V≥9V（PD 握手后 type 仍报 DCP，靠 VBUS 电压反推）；电流≥0.5A 普通、否则涓流。
- 电池主功率口径不变：UI 一律 `battery V×|I|`，`power_now` 仅进 CSV RAW。

### 14.6 热区与 cooling 多厂商

- **结温白名单**（`isCpuThermalName`）：高通 `cpuss/cpu/gpuss`、MTK `mtktscpu/mt-cpu/mttcpu`、Exynos `big-thermal/little-thermal/g3d`、麒麟 `cpu0/cpu1/gpu`、Tensor `cpuN-thermal/gpu-thermal`、通用 `soc/ap`。
- **黑名单**：`tof-therm`（恒定伪值）、`xo-therm`、`usb-therm`。
- **外壳 skin**：`skin*` / `quiet_therm` / `mtktsskin` / `skin-msm-therm` 等，多厂商模式匹配。
- **Thermal HAL**：`dumpsys thermalservice` 解析 `Temperature{mValue, mType}`，type=0 CPU / 1 GPU / 2 battery / 3 skin，5s 节流，Android 10+ 通用。
- **cooling 模式匹配**（`isCoolingRelevant`）：`thermal-cpufreq*` / `thermal-devfreq*` / `mali` / `kgsl` / `ddr` / `gpu` / `display` / `panel` / `battery` / `cdsp` / `ufs` / `wlan`，不用纯枚举。

### 14.7 UI 自适应

- **分核频率/占用**：按 `cores.size` 渲染，网格 `chunked(4)`（4核2列、8核4列、9核3行末行1格、10核3行）。
- **簇图例**：按 `cores` 的 cluster label 去重动态生成，显示 `label×核数`（如「X2×1 / A710×3 / A510×4」）。
- **档位驻留**：动态取最低频簇（maxMHz 最小），`time_in_state` 路径取该簇首个核，不写死 A510/cpu0。
- **簇上限**：遍历所有簇动态显示 `label上限 = maxMHz`，不写死 X2/A510。
- **远端颜色**：MonitorScreen/RemoteDetailScreen 按 `maxFreqs` 降序推断角色，规则与本机 CpuTopology 一致（n>=3 时中间簇 PERFORMANCE 蓝）。
- **缺失**：任何上限/频率读不到显示「–」/灰，不伪造、不以零顶替。

### 14.9 SoC 平台识别（v0.23.0，PlatformDetector）

**核心原则：识别硬件平台，而非枚举机型。** 运行时采集始终以 sysfs/proc 文件存在性探测为准，平台识别只提供元信息 + 语义修正，绝不硬编码节点路径。

- **识别信号**（按优先级）：`ro.soc.manufacturer` → `ro.board.platform` → `ro.soc.model` / `Build.SOC_MODEL` → `Build.HARDWARE` → `Build.BOARD`。
- **读取方式**：优先反射 `android.os.SystemProperties.get()`（快、无进程开销），失败回退 `getprop` 命令（兼容）；结果进程级缓存（`@Volatile` + `synchronized` 双重检查），平台恒定不变。
- **平台枚举**：`QCOM / MTK / EXYNOS / HISILICON / GOOGLE_TENSOR / SAMSUNG / UNKNOWN`，每个带 `tag`（协议用，如 `qcom`）和 `friendlyName`（UI 展示，如「高通 Qualcomm」）。
- **高通代号→商用名映射**（`ro.board.platform` 小写匹配）：

| boardPlatform | 商用名 | boardPlatform | 商用名 |
|---|---|---|---|
| msmnile | 855 | kona | 865 |
| kona_ac | 870 | lahaina | 888 |
| taro | 8 Gen 1 | kalama | 8 Gen 2 |
| pineapple | 8 Gen 3 | sun | 8 Elite |
| atoll | 765G | shima | 778G |
| cape | 7+ Gen 2 | holi | 695 |

- **soc.model 补充映射**：`SM8450→8 Gen 1`、`SM8475→8+ Gen 1`、`SM8550→8 Gen 2`、`SM8650→8 Gen 3`、`SM8750→8 Elite` 等；查不到时回退 `ro.soc.model` 原文（如 `SM8450`）。
- **用途**：① UI 设备信息卡展示平台类型 + 商用名 + boardPlatform；② 状态语义修正（见 14.10）；③ 未来厂商补丁挂钩点。
- **A41 实测**：`platform=qcom`、`socName=Snapdragon 8 Gen 1`、`boardPlatform=taro`、`socModel=SM8450`。

### 14.10 单位阈值归一化（v0.23.0，Units）

不同厂商 sysfs 节点的频率/电压/电流单位不统一（有的 kHz 有的 MHz，有的 µV 有的 mV），按原始值量级自动判定单位。

| helper | 阈值 | 判据 | 换算 |
|---|---|---|---|
| `Units.cpuFreqMHz(raw)` | 100_000 | raw > 100_000 → kHz；1..100_000 → MHz | kHz ÷1000；MHz 直读 |
| `Units.voltageV(raw)` | 100_000 | raw > 100_000 → µV；否则 → mV | µV ÷1e6；mV ÷1e3 |
| `Units.currentA(raw)` | 10_000 | raw > 10_000 → µA；否则 → mA | µA ÷1e6；mA ÷1e3 |

- **量级依据**：CPU 频率 MHz 范围 300–5000、kHz 范围 300000–5000000+；电压 µV 3–5V=3000000–5000000、mV 3000–5000；电流 µA 0.5–3A=500000–3000000、mA 500–3000。阈值留有充足裕度。
- **RAW 铁律**：`CpuCore.freqKHz/maxKHz`、`BatteryData.inputVoltUv/inputCurUa` 始终保存原始值零换算，归一化只作用于展示层（MHz/V/A）；CSV RAW 区原样输出。
- **应用范围**：CpuReader 的 `scaling_cur_freq` / `scaling_max_freq` / `cpuinfo_max_freq`（含 60s 缓存）；BatteryReader `readAdapterInput` 的输入侧电压电流。电池主侧 `voltage_now`/`current_now` 仍按惯例 µV/µA（A41 及绝大多数机型一致），暂不归一化。
- **GPU 频率**：保留 `GpuReader.freqFromRaw` 专用逻辑（Hz/kHz 量级，1..9999 判据），与 CPU 频率量级不同，不共用。

### 14.11 状态语义按平台修正（v0.23.0）

`GpuReader.freqState` 在原有「已提权读不到→UNAVAILABLE、未提权→NEED_PRIV」基础上，增加平台感知分支：

- **QCOM 平台但 `/sys/class/kgsl` 目录不存在** → `UNAVAILABLE`（本平台无此节点，即使提权也读不到，提示「本平台无此节点」而非误导用户去提权）。
- **QCOM 平台且 kgsl 存在但 App 域 EACCES** → `NEED_PRIV`（权限不够，提权后可读）。
- 其余平台保持原有逻辑。

此规则可扩展到其他读数：读不到的节点，能区分「平台没有」与「权限不够」时优先给准确语义。

### 14.12 supported_devices.csv 定位

`supported_devices.csv`（如有）仅作为**画像参考 / 社区反馈库**，记录已验证机型的硬件规格与节点路径，供开发参考和用户上传积累；**不参与运行时机型匹配**。运行时一切从 sysfs/proc 动态探测 + 平台识别元信息，与「识别硬件而非机型」原则一致。
### 14.13 已知限制

- **除 A41 外均为静态保证**：动态分簇/CPU part/GPU 探测/电源枚举/热区匹配均基于 sysfs 标准与调研数据实现，代码逻辑通过审查，但未在 MTK/Exynos/Tensor/麒麟真机上实际运行验证。
- **Thermal HAL**：三方 App 无 DUMP 权限，`dumpsys thermalservice` 仅在 Shizuku/Root 档可用；免提权时回退 sysfs 热区。
- **麒麟 9000S/9010/9020**：自研 TaiShan 核 + Maleoon GPU，sysfs 节点闭源，part 识别可能回退通用名。
- **Tensor G5**：已切 PowerVR GPU，devfreq 目录名需真机采样确认。
- **协议兼容性**：v0.22 被监控端（非 A41 机型）→ v0.21 监控端时，簇颜色可能落默认蓝（旧端硬编码 X2/A710/A510），但不崩溃不丢数据。
